## Phase Goal

**As a** Govi customer, **I want to** browse product categories, pick a question, and read the answer, **so that** I can get instant product help via Messenger without waiting for a human.

(Phase 3 vertical slice — this plan completes the user-visible half. Plan 01 shipped the API.)

<objective>
Wave 1 of the Phase 3 MVP vertical slice. Wire the Messenger bot to the listing endpoint introduced by Plan 01 (`GET /content?type=...&category=...`) and to the existing single-item endpoint (`GET /content/{id}`). After this plan ships, the full menu → category → question → answer flow works end-to-end against a real (or local) FastAPI backend, with every error path gracefully landing the user back on the main menu.

Purpose: Phase 1 stood up navigation skeleton (welcome + main menu quick replies + free-text fallback) but the "Product Help" quick reply currently dead-ends — `handleWebhookEvent` logs the payload and returns. Phase 3 turns that dead-end into the real product Q&A flow. Plan 01 made the data reachable; Plan 02 makes the data visible to customers.

Output:
- Modified `messenger-bot/src/index.ts`: three new handlers (`sendCategoryMenu`, `sendQuestionMenu`, `sendAnswer`), two new module constants (`PAYLOAD_PREFIX_CATEGORY`, `PAYLOAD_PREFIX_QUESTION`), and an extended quick_reply dispatcher inside `handleWebhookEvent`. The dispatcher routes by payload prefix: `MENU_PRODUCT_HELP` → categories, `CATEGORY:<id>` → questions, `QUESTION:<id>` → answer. All three handlers wrap their axios call in try/catch and emit a user-facing apology + main menu on failure.
- New `messenger-bot/src/tests/qa-flow.test.ts`: four test cases covering the three happy paths plus the API-error fallback, following the node:test + axios.post stubbing pattern already established in Phase 1 tests.
</objective>

New module-level string constants this plan introduces:

  PAYLOAD_PREFIX_QUESTION = "QUESTION:"

  Both are SCREAMING_SNAKE_CASE per project convention (CLAUDE.md naming rules). They MUST be exported so tests can reference them by symbol rather than string-duplicating the literal.

New handler signatures:
  async function sendCategoryMenu(recipientId: string): Promise<void>
  async function sendQuestionMenu(recipientId: string, categoryId: string): Promise<void>
  async function sendAnswer(recipientId: string, questionId: string): Promise<void>

Quick reply payload routing inside handleWebhookEvent.quick_reply branch:
  payload === "MENU_PRODUCT_HELP"                    -> sendCategoryMenu(senderId)
  payload === "MENU_CONTACT_HUMAN"                   -> noop in this phase (Phase 4 owns it; log only)
  payload.startsWith(PAYLOAD_PREFIX_CATEGORY) === true   -> id = payload.slice(PAYLOAD_PREFIX_CATEGORY.length); sendQuestionMenu(senderId, id)
  payload.startsWith(PAYLOAD_PREFIX_QUESTION) === true   -> id = payload.slice(PAYLOAD_PREFIX_QUESTION.length); sendAnswer(senderId, id)
  otherwise                                           -> sendFallbackMessage(senderId)  (unknown payload — re-anchor)

Error policy for the three new handlers:
  - Any axios error or non-2xx status MUST result in a single sendMessage call with text "Something went wrong fetching that — back to the main menu:" AND quickReplies = MAIN_MENU_QUICK_REPLIES.
  - Error log uses console.error with axios.isAxiosError(err) guarded branch — copy the exact pattern from sendMessage in index.ts so PAGE_ACCESS_TOKEN is never logged (SEC-03 preservation).
  - Empty-result handling (`items: []`) is treated as success, NOT as an error: the bot sends a polite "No questions in that category yet — back to the main menu:" with MAIN_MENU_QUICK_REPLIES. (Test asserts this exact dispatch.)
  - sendAnswer 404 is treated as an error path (the API said the content does not exist) — same fallback.

Messenger constraints (already documented in Phase 1 PITFALLS.md):
  - Quick reply `title` must be ≤ 20 chars. Plan 01 enforces this on the data side (vault-sample titles). Bot does NOT trim — it relies on the data being correct.
  - Quick reply `payload` must be ≤ 1000 chars. `CATEGORY:` + id and `QUESTION:` + id will be tens of chars — well under the limit.
  - Quick reply array max length is 13 buttons. If a category has more than 12 questions, sendQuestionMenu MUST truncate to the first 12 and append a 13th "Main menu" reply so the user is never stranded. This is the only place truncation logic lives.

    ```
    function withAxiosStubs(opts: { onGet?: (url: string) => any; onPost?: (url: string, body: any) => any }) {
      // eslint-disable-next-line @typescript-eslint/no-require-imports
      const axios = require("axios");
      const originalPost = axios.post;
      const originalGet = axios.get;
      const getCalls: { url: string }[] = [];
      const postCalls: { url: string; body: any }[] = [];
      axios.get = async (url: string) => {
        getCalls.push({ url });
        if (opts.onGet) return opts.onGet(url);
        return { data: {} };
      };
      axios.post = async (url: string, body: any) => {
        postCalls.push({ url, body });
        if (opts.onPost) return opts.onPost(url, body);
        return { data: {} };
      };
      return {
        getCalls,
        postCalls,
        restore() { axios.post = originalPost; axios.get = originalGet; },
      };
    }
    ```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Facebook → bot | Webhook events carry user-controlled `quick_reply.payload` strings. Phase 1 HMAC verification confirms the sender is Facebook, but Facebook is a relay — the actual payload value came from the customer's tap on a button the bot itself rendered, OR from a crafted POST that bypassed the user-facing UI but cleared HMAC (the page operator or someone with the app secret). Either way, the payload string MUST be treated as untrusted input downstream. |
| bot → FastAPI | The bot uses payload-derived ids (`<id>` from `CATEGORY:<id>` or `QUESTION:<id>`) to build URLs to the local FastAPI service. URL construction is an injection surface (extra query parameters, path traversal). |
| FastAPI → bot | Response bodies are operator-controlled vault content. Treated as trusted (operator runs both services). |
| bot → Facebook Graph API | Outgoing `sendMessage` calls carry vault-sourced answer bodies as message text. Facebook renders this as plain text (no markdown / HTML rendering in Messenger text bubbles), so XSS-in-message is not a concern. |
