## Phase Goal

**As a** Govi customer, **I want to** browse product categories, pick a question, and read the answer, **so that** I can get instant product help via Messenger without waiting for a human.

(Phase 3 vertical slice — this plan delivers the API half. Plan 02 delivers the bot half.)

<objective>
Wave 0 of the Phase 3 MVP vertical slice. Add a single listing endpoint to the existing FastAPI content router so the bot (Plan 02) can discover categories and questions without hard-coding IDs. Also create a handful of sample vault files that demonstrate the Phase 3 content schema — these double as test fixtures and as a real seed that an operator can copy into their Obsidian vault.

Purpose: The FastAPI content API currently exposes only `GET /content/{id}` and `POST /content/reload`. The bot has no way to ask "what categories exist?" or "what questions live under category X?" — both required by QA-01 and QA-02. Without a listing endpoint the bot would need a hard-coded config file, which violates D-Init (Obsidian vault is the single content source — admins must not edit code to manage content).

Output:
- Modified `app/routers/content.py`: a `category` field threaded through the loader (optional string), plus a new `GET /content` endpoint with `?type=...&category=...` query filters and a small `ContentListResponse` model wrapping `items: list[ContentListItem]`.
- Modified `tests/test_content.py`: four new test cases covering the listing endpoint (filter by type, filter by type+category, empty result, missing type validation). All eight pre-existing tests continue to pass untouched.
- New `vault-sample/` directory at the repo root with five `.md` files demonstrating the category/question schema. Operators copy these into their real Obsidian vault as a seed; tests do NOT load from `vault-sample/` — they continue to use `tmp_path`.
</objective>

Existing endpoint (DO NOT BREAK):
  GET /content/{content_id}
    200 -> {"id": str, "type": str, "title": str, "body": str}
    404 -> {"detail": "Content not found"}

New endpoint added by this plan:
  GET /content?type={type}&category={optional_category}
    200 -> {"items": [{"id": str, "type": str, "title": str}, ...]}
    400 -> {"detail": "type query parameter is required"}    (when type is missing or empty string)

  Notes:
    - Listing items intentionally OMIT `body` to keep menus small.
    - `?type=category` returns ALL items where item["type"] == "category" (category param ignored for categories).
    - `?type=question&category=cat-X` returns items where item["type"] == "question" AND item["category"] == "cat-X".
    - `?type=question` (no category) returns ALL question items regardless of category — Plan 02 will only call this with a category, but the endpoint stays general.
    - Items in `items` are sorted by `id` ascending for deterministic menu ordering.
    - An unknown category produces `{"items": []}` (not 404). The caller treats empty as "no questions yet".

Loader behaviour for the new `category` field:
    - `meta.get("category")` is optional; if present it MUST be a non-empty string, else the file is skipped with a logger.warning (matches existing strict validation style for id/type/title).
    - If `category` is absent, the item is stored without a `category` key (i.e., `category` is None / not set). This is valid for category-type files, which themselves do not belong to a category.
    - The `ContentResponse` returned by GET /{id} does NOT include `category` — that field is internal to the loader and to the listing filter. The single-item shape stays `{id, type, title, body}` for backwards compatibility.

Module-level state that already exists and MUST NOT be renamed:
  app.routers.content._vault              # dict[str, dict]
  app.routers.content.load_vault          # callable
  app.routers.content.router              # APIRouter(prefix="/content", tags=["content"])
  app.routers.content.ContentResponse     # BaseModel{id,type,title,body}

New names this plan adds:
  app.routers.content.ContentListItem     # BaseModel{id, type, title}
  app.routers.content.ContentListResponse # BaseModel{items: list[ContentListItem]}

Pitfall: FastAPI route ordering. The new `@router.get("")` MUST be declared BEFORE the existing `@router.get("/{content_id}")` so that `/content` does not match the path parameter. Test will catch this: a request to `/content?type=category` must NOT be routed to the `/{content_id}` handler.

       async def list_content(
           type: str = Query("", description="Required. Filter by item type, e.g. 'category' or 'question'."),
           category: Optional[str] = Query(None, description="Optional. When type='question', restrict to a category id."),

           if not type:

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| network → process | Anyone reachable on the FastAPI port can call GET /content (listing), GET /content/{id}, POST /content/reload. CORS remains `allow_origins=["*"]` (Phase 2 baseline; tightening is a Phase 5 concern). |
| filesystem → process | Vault directory contents (operator-controlled) are parsed as YAML + markdown. Plan 03 adds an OPTIONAL `category` field; type rules tighten as a result. |
| query string → process | New listing endpoint accepts `type` and `category` as untrusted query parameters. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-01 | Tampering | `type` query parameter accepts arbitrary strings | mitigate | The listing handler iterates `_vault.values()` and compares `item["type"] == type`. Only items whose loaded type matches are returned. Type is never used to look up files, build paths, or run code — it is only used for an equality check. Worst case: caller supplies an unknown type (e.g., `?type=admin`) and receives `{"items": []}`. No information leakage beyond "this type yields zero results", which is also true for empty categories (existing accepted threat T-2-03 family). No allow-list enforcement needed at the API layer because the data layer already enforces it via equality. |
| T-3-02 | Tampering | `category` query parameter accepts arbitrary strings | mitigate | Same shape as T-3-01: equality check against `item.get("category")`. Unknown category yields empty list (covered by test_list_unknown_category_returns_empty). No SQL, no filesystem path construction, no shell — the only sink is a Python dict comparison. |
| T-3-03 | Information Disclosure | Listing response includes id/type/title for every enabled item of the requested type | accept | Same disposition as T-2-03 (existing /health content_count exposure). The vault is non-sensitive customer-support Q&A. Listing exposes titles by design — that is the menu surface. Operators control what is in the vault. |
| T-3-04 | Denial of Service | Unbounded listing on a large vault | accept | Bounded by vault size. Same operator-controlled-input disposition as T-2-05 (oversized .md). For v1 deployments the vault is small (dozens of Q&As). If vault size grows, paginate; not in scope for v1. |
| T-3-05 | Spoofing | Malformed `category` value in vault frontmatter (e.g., a YAML list `category: [a, b]`) | mitigate | Task 1 step 3 adds a strict check: `category` must be a non-empty string if present, else the file is skipped with a warning. Matches the existing strict validation pattern for id/type/title. Files that fail validation never enter `_vault` and cannot be served. |
| T-3-06 | Information Disclosure | Listing endpoint URL ordering pitfall — `/content` would route to `/{content_id}` and return 404 detail "Content not found" leaking the existence of the single-item handler | mitigate | Task 1 mandates source-order: `@router.get("")` is declared BEFORE `@router.get("/{content_id}")`. test_list_missing_type_returns_400 asserts the listing handler is reached (returns our specific 400 detail, not the 404 detail), proving the route order is correct. |
| T-3-07 | Tampering | `category` field treated as an ID reference but never validated against existing categories | accept | A question may reference a non-existent category id. The listing endpoint surfaces it correctly to its declared category; if no category file exists with that id, the bot in Plan 02 simply never offers a path to it. This is a content-quality issue, not a security one. Validation of cross-references is a v2 admin-tooling concern. |
</threat_model>
