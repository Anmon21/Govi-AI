<objective>
Vertical slice 1: **the bot is secure**. After this plan, a forged POST returns 403, every Graph API call checks for errors-in-200, and the catch blocks no longer leak `PAGE_ACCESS_TOKEN` through log output. This is the security half of the Phase 1 goal — independently verifiable before any UX changes land in Plan 03.

Three connected security fixes plus a Graph API version bump, all in `messenger-bot/src/index.ts`:

1. **SEC-01 (D-03, D-06)** — Replace global `app.use(express.json())` with route-level `express.raw({ type: '*/*' })` on `POST /webhook`, then run a new `verifySignature` middleware that HMAC-verifies the raw body against `X-Hub-Signature-256` using `crypto.createHmac` and `crypto.timingSafeEqual`. Gated on `FACEBOOK_APP_SECRET` — when absent, log a warning and pass through (developer-local-friendly per D-03).
2. **SEC-02 (D-07)** — After every `axios.post` to `graph.facebook.com`, check `response.data?.error` and log it; Facebook returns failures inside HTTP 200.
3. **SEC-03 (D-08)** — Every catch block that handles an axios error must log only `axiosErr.message` and `axiosErr.response?.data`. The existing catch in the POST handler (line 53-56) is the canonical leak path and is replaced.

Plus: **Graph API version bump v19.0 → v21.0** in `sendMessage` (RESEARCH.md state-of-the-art; one-line change inside the same edit).

Purpose: Per ROADMAP success criterion #1 and #5, "Sending a forged (invalid signature) POST to /webhook returns 403 — the bot does not process it" and "PAGE_ACCESS_TOKEN does not appear in any log output". This plan is the only place those become true. Plan 03 layers UX on top of a now-secure transport.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Facebook → bot `/webhook` | Untrusted POST body crosses here; integrity proven by HMAC-SHA256(rawBody, FACEBOOK_APP_SECRET) matching `X-Hub-Signature-256` header |
| bot → Facebook Graph API | Trusted outbound; failure modes include errors-in-200 (SEC-02) and exceptions whose `config.url` contains `PAGE_ACCESS_TOKEN` (SEC-03) |
| bot → Govi AI (FastAPI) | Internal trusted boundary; existing catch leaks token through identical pattern, fixed under SEC-03 |
| log output → developer / log aggregator | Logs must not carry `PAGE_ACCESS_TOKEN` or `FACEBOOK_APP_SECRET` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-01 | Spoofing (V4 Access Control) | `POST /webhook` handler | mitigate | `verifySignature` middleware computes HMAC-SHA256 over the raw body using `crypto.createHmac` and compares with `crypto.timingSafeEqual`; returns 403 on mismatch, missing header, or buffer length disparity (SEC-01) |
| T-1-02 | Spoofing — timing attack on HMAC compare | `verifySignature` | mitigate | Uses `crypto.timingSafeEqual` (constant-time) — never `===` or `==` on the digests (V6 Cryptography) |
| T-1-03 | Denial of Service (silent send failure) | `sendMessage` | mitigate | After `axios.post`, check `response.data?.error` and log message + body so failures are visible (SEC-02) |
| T-1-04 | Information Disclosure (token in logs) | catch blocks in `sendMessage` AND in the POST `/webhook` handler's Govi AI call | mitigate | Catch typed as `AxiosError`; log only `axiosErr.message` and `axiosErr.response?.data` — never the full `err` (which carries `config.url` with `access_token` query param) (SEC-03) |
| T-1-05 | Tampering — request body mutated between HMAC check and parse | `verifySignature` → handler | mitigate | HMAC is verified over the raw Buffer; only AFTER verification is `JSON.parse` called and the result stored on `(req as any).parsedBody`; handler reads `parsedBody`, not `req.body` |
| T-1-06 | Information Disclosure — APP_SECRET leak via warning logs | startup guard | accept | Guard logs only the literal phrase "FACEBOOK_APP_SECRET not set" — never the value; the value path is `process.env`, no echoing |
| T-1-07 | Denial of Service — `ERR_CRYPTO_TIMINGSAFEEQUAL_ARRAY_BUFFER_LENGTH` crash on malformed signature | `verifySignature` | mitigate | Pre-check `expectedBuf.length !== signatureBuf.length` and 403 early — never invoke `timingSafeEqual` on different-length buffers (Pitfall 2) |
| T-1-08 | Spoofing — wrong APP_SECRET breaks all real traffic with no diagnostic | `verifySignature` | mitigate | On length mismatch or 403 path, log `"Webhook signature mismatch — check FACEBOOK_APP_SECRET"` once per failure — distinguishes forged event from misconfigured secret (Pitfall 3) |
| T-1-09 | Repudiation — bot can be configured with no APP_SECRET and silently process forged events | Startup guard + `verifySignature` | accept (with caveat) | Per D-03, no-APP_SECRET state is a documented developer-local mode; the startup warning logs the degraded state at every boot so it cannot ship to prod unnoticed |
</threat_model>
