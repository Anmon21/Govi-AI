<objective>
Add the consolidated page-config write endpoint (D-02) the Phase 15 admin editor will
call: `PUT /pages/{page_id}/config`, a whole-row replace of the `page_configs` row
carrying `welcome_text` (CONTENT-01), `menu_json` (CONTENT-02, the flat
`[{title,payload}]` array of D-04), `escalation_psid` and `escalation_message`
(CONTENT-04). JWT-authenticated via `get_current_tenant` and tenant-ownership scoped.

Also add the INTERNAL read path the ROADMAP goal ("...content is **served** from the
database per Page ID") and Phase 14 (BOT-01: "fetches the matching token + config from
the database") require: `GET /internal/pages/{page_fb_id}/config`, HMAC-guarded and
keyed on the Facebook `page_fb_id`, mirroring the existing
`/internal/pages/{page_fb_id}/access-token` bot-facing endpoint. This does not contradict
D-02 (D-02 fixed only the write shape; it did not prohibit a read); no JWT admin GET is
added — config pre-fill for the editor is a Phase 15 concern, out of scope here.

Purpose: Deliver three content-write requirements in one atomic PUT and give the bot a
defined mechanism to read welcome/menu/escalation config.
Output: PUT + internal GET endpoints and models in `app/routers/pages.py`, tests in
`tests/test_pages.py`.

Note: `page_id` in the PUT path is the INTERNAL integer `pages.id` (a tenant-scoped
resource); `page_fb_id` in the internal GET path is the Facebook id (bot-facing).
Keep this distinction explicit in code, docstrings, and tests.
</objective>

    `async def put_page_config(page_id: int, request: PageConfigRequest,
    current: dict = Depends(get_current_tenant))`. In the docstring, state explicitly that

       (page_id, welcome_text, menu_json, escalation_psid, escalation_message) VALUES (?,?,?,?,?)`.

       used in the schema defaults.
    5. `conn.commit()`, then re-`SELECT welcome_text, menu_json, escalation_psid,
       escalation_message, updated_at FROM page_configs WHERE page_id = ?`.

       `json.loads(row["menu_json"])`. `conn.close()` in `finally`.
