### test_login_invalid(db_client) — SC-1
- Make THREE login attempts and assert each returns 401:
  1. Wrong password: POST /auth/login with valid email + wrong password — assert 401, body["detail"] == "Invalid credentials"
  2. Unknown email: POST /auth/login with "nonexistent@example.com" + any password — assert 401, body["detail"] == "Invalid credentials"
  3. Empty password: POST /auth/login with valid email + "" — assert 401 (passes Pydantic, fails bcrypt verify)
- All three responses MUST have identical detail strings (no user enumeration)

### test_inactive_tenant(db_client) — SC-4
- Step 1: create a client via super-admin token (login as super-admin, get token, POST /admin/tenants to create "client@test.local" / "client-pass") — assert 201
- Step 2: manually deactivate the new client via direct SQL: `get_connection(db_client.db_path)` + `UPDATE tenants SET is_active = 0 WHERE email = 'client@test.local'` + commit + close
- Step 3: POST /auth/login with client@test.local + client-pass — assert 401 (deactivated tenants cannot log in even with correct password)

### test_create_tenant(db_client) — TENANT-01
- Login as super-admin, get JWT
- POST /admin/tenants with {"email": "new@test.local", "password": "new-pass"} and Authorization: Bearer <token>
- Assert status_code == 201
- Assert response JSON has fields {id, email, is_active, is_super_admin, created_at} and NO password_hash key
- Assert response.json()["email"] == "new@test.local", is_active is True, is_super_admin is False
- Assert direct DB query confirms the row exists and `password_hash` starts with `$2b$` or `$2a$` (bcrypt prefix) and is NOT the plaintext "new-pass"

### test_duplicate_email(db_client) — TENANT-01
- Login as super-admin
- Create a client via POST /admin/tenants — assert 201
- POST /admin/tenants again with the SAME email and a different password — assert 409, body["detail"] == "Email already exists"

### test_list_tenants(db_client) — TENANT-02
- Login as super-admin
- Create two clients via POST /admin/tenants ("c1@test.local", "c2@test.local")
- (Optional: insert a row directly into pages table with tenant_id of c1, is_active=1, to verify page_count > 0; use direct SQL with get_connection)
- GET /admin/tenants with Authorization: Bearer <super-admin-token>
- Assert status_code == 200
- Assert response is a list of length 2 (super-admin row excluded — Pitfall 4)
- Assert every item has the keys {id, email, is_active, created_at, page_count}
- Assert no item has email == db_client.super_admin_email
- If a page was seeded for c1, assert that c1's TenantListItem has page_count >= 1; c2 has page_count == 0

### test_soft_delete(db_client) — TENANT-03, SC-4
- Login as super-admin
- Create a client "delete-me@test.local" via POST /admin/tenants — capture the returned id
- Seed a page directly via SQL: `INSERT INTO pages (tenant_id, page_fb_id, page_name, is_active) VALUES (?, 'fb-123', 'Test Page', 1)`
- DELETE /admin/tenants/{client_id} with super-admin token — assert 200, body["pages_deactivated"] == 1, body["detail"] startswith "Tenant " and contains "deactivated"
- Direct SQL: assert tenants.is_active == 0 for client_id AND pages.is_active == 0 for the seeded page
- Second DELETE on the same id — assert 404 (already inactive)
- DELETE on the super-admin's own id — assert 403, body["detail"] == "Cannot delete your own account"

### test_tenant_isolation(db_client) — SC-5
- Login as super-admin and create two clients: A ("a@test.local", "pass-a") and B ("b@test.local", "pass-b") — capture both ids
- Login as A: POST /auth/login with A's credentials, get token_a
- Login as B: POST /auth/login with B's credentials, get token_b
- GET /tenants/me with token_a — assert 200, body["id"] == a_id, body["email"] == "a@test.local"
- GET /tenants/me with token_b — assert 200, body["id"] == b_id, body["email"] == "b@test.local"
- Confirm responses are different (A's token returns A's row, never B's)
- Assert neither response contains a password_hash key

### test_forbidden(db_client) — SC-5
- Login as super-admin, create a client
- Login as the client (POST /auth/login with client creds), get client_token (role="client")
- GET /admin/tenants with Authorization: Bearer <client_token> — assert 403, body["detail"] == "Admin access required"
- POST /admin/tenants with client_token + new tenant body — assert 403
- DELETE /admin/tenants/{some_id} with client_token — assert 403
- GET /admin/tenants with NO Authorization header — assert 401 (Bearer scheme required)
- GET /admin/tenants with Authorization: Bearer garbage.token.value — assert 401, body["detail"] == "Invalid token"

  <how-to-verify>
    1. Ensure JWT_SECRET, SUPER_ADMIN_EMAIL, SUPER_ADMIN_PASSWORD are set in .env. If you have not generated a JWT_SECRET yet, run:
       `python3 -c "import secrets; print(secrets.token_urlsafe(48))"` and paste into .env as JWT_SECRET=...

    2. Initialize the dev DB (one-time): `python3 scripts/init_db.py` — should print schema initialized + super-admin seeded.

    3. Start the FastAPI server: `python3 main.py` (uvicorn on APP_PORT, default 8000).

    4. In a separate terminal, request a token using the super-admin credentials from .env:
       ```
       curl -s -X POST http://localhost:8000/auth/login \
         -H 'Content-Type: application/json' \
         -d '{"email":"<SUPER_ADMIN_EMAIL>","password":"<SUPER_ADMIN_PASSWORD>"}'
       ```
       Expected response: `{"access_token":"eyJ...","token_type":"bearer"}`. The token MUST start with `eyJ` (base64-encoded `{"alg":...`).

    5. Copy the access_token value. Open https://jwt.io in a browser. Paste the token into the "Encoded" panel on the left.

    6. Inspect the decoded payload (right panel). Confirm ALL of the following:
       - Header shows `{"alg":"HS256","typ":"JWT"}` — alg MUST be HS256 (not "none", not "RS256")
       - Payload `sub` is a string (numeric value but as a quoted string, e.g. `"1"`)
       - Payload `role` is exactly `"super_admin"` (no other value, no whitespace)
       - Payload `exp` is a Unix timestamp approximately 7 days from now (compare to current date). At https://www.epochconverter.com it should resolve to a date about a week away.
       - Three segments separated by dots (header.payload.signature) — no extra segments

    7. (Optional sanity check) Paste your JWT_SECRET into the "Verify Signature" field at jwt.io and confirm the "Signature Verified" green badge appears. This proves the secret in .env actually signs the tokens (and that the secret is HMAC-compatible).

    8. Stop the server (Ctrl+C).
  </how-to-verify>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Test harness -> production routes | tests exercise the real FastAPI routes via TestClient; same boundary as production |
| Direct DB SQL in tests -> tenants/pages tables | tests bypass the API to insert pages and deactivate tenants — used only to set up isolated test conditions, not to bypass auth |
| Human eyes -> external jwt.io | the only out-of-band validation step; trust scope is the human's browser session |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-19 | Information Disclosure | Test fixtures leaking credentials | accept | Test credentials ("admin-pass", "client-pass") are hardcoded in test code only; never written to production DB; tmp-path DB is destroyed after each test |
| T-11-20 | Tampering | Test bypasses real auth via direct SQL | accept | Tests use direct SQL ONLY to seed pre-conditions (inactive tenants, pages); the assertion path still goes through /auth/login and the protected routes, so the auth surface is fully exercised |
| T-11-21 | Repudiation | Manual jwt.io check has no audit trail | accept | This is a one-shot manual validation; the resume-signal records human approval inline in the execution log |
| T-11-22 | Information Disclosure | Pasting JWT_SECRET into jwt.io | mitigate | Step 7 is OPTIONAL; if performed, the secret is sent only to jwt.io's local browser-side JS (jwt.io explicitly does not transmit secrets to its server, per their FAQ). User can skip this step if uncomfortable |
| T-11-23 | Spoofing | Forged JWT in test_forbidden | mitigate | Test uses literal string "garbage.token.value" — verify_token returns 401, proving signature validation rejects unsigned/malformed tokens |
</threat_model>
