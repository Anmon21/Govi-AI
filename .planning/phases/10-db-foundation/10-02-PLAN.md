<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Environment (.env) → app/config.py.Settings | The Fernet key crosses from the host environment into the Python process; .env is gitignored and never committed |
| app/config.py.settings → app/crypto.py._fernet | The key is read from settings at call time and used to construct a Fernet instance; it must not be cached on disk or in any persistent store |
| app/crypto.py → SQLite database (Phase 12) | Only ciphertext crosses this boundary; the key itself NEVER reaches the DB |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-KEY | Information Disclosure | app/crypto.py and app/config.py — Fernet key | mitigate | Key sourced ONLY from settings.fernet_key (pydantic-settings env loader). Acceptance criteria grep gates ensure app/crypto.py contains no hardcoded key (`gAAAAA` or `FERNET_KEY=`), no sqlite3 imports, no file writes, no print calls. .env is gitignored; .env.example carries only a placeholder + generation command (grep gate rejects any 40+ char base64-shaped value in the example). Em-dash source comment documents the constraint for future maintainers. |
| T-10-CRYPTO-ROLL | Tampering | app/crypto.py — choice of primitive | mitigate | Use cryptography.fernet.Fernet (AES-128-CBC + HMAC-SHA256), not a hand-rolled AES wrapper — per "Don't Hand-Roll" in RESEARCH.md. Fernet handles IV generation and authentication tag, preventing IV-reuse and tampering vulnerabilities common in hand-rolled symmetric crypto. |
| T-10-KEY-STARTUP | Denial of Service | Application boot when FERNET_KEY unset | accept | Phase 10 uses lazy validation (key checked at first encrypt/decrypt call, not at import) — per RESEARCH.md Open Question 2 recommendation. Phase 12 (first real consumer) will add startup validation. Acceptable for Phase 10 because no request path uses the key yet. |
</threat_model>
